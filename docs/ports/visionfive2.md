# VisionFive2 (昉·星光2, StarFive JH7110) — 地址清单 (供人工核对)

> 本仓库**不使用设备树**。这份清单是那个取舍要求的人工核对入口。
> 用 `cargo xtask info --config riscv64-visionfive2` 打印内核实际
> 使用的值, 与本表对照。

## 内存

| 项目 | 值 | 出处 / 说明 |
|---|---|---|
| DRAM base | `0x40000000` | JH7110 内存映射 (**与 QEMU 的 0x80000000 不同**) |
| DRAM size | `128 MiB` | 板载有 2/4/8 GB, 这里保守地只用前 128 MiB |
| firmware base | `0x40000000` | OpenSBI 起点 |
| kernel base | `0x40200000` | 固件跳转地址; 必须等于 `kernel_load_addr` |

**为什么只用 128 MiB**:

1. 教学内核不需要那么大内存;
2. U-Boot 可能把内核/initrd 放在高端地址, 小范围管理更安全;
3. 128 MiB 是一个自洽的检查点 —— 若真实可用内存更小, 说明这块
   板子和假设不符, 应当先怀疑常量而不是代码。

## CPU

| 项目 | 值 | 出处 / 说明 |
|---|---|---|
| 物理核 | 4 × U74 应用核 + 1 × S7 监控核 | JH7110 = 4+1 核 |
| ncpu | `4` | 内核可用的 U74 数量 |
| hart range | `[1, 4]` (**闭区间, 不含 0**) | hart 0 是 S7, 被 U-Boot/OpenSBI 占用 |
| boot hart | `1` | U-Boot 把内核跑在 hart 1 上 |

### 这是移植时最容易写错的地方

如果启动代码里写的是 `hartid < ncpu`:

```text
  ncpu = 4
  -> hart 4 这个**合法**的核会被判定为非法而不启动
  -> 症状是 "4 核系统只起来 3 个核"
  -> 而且**不报任何错** —— 因为多核启动是异步的
```

同理, 栈的索引必须用 `hartid - harts.min`:

```text
  用 hartid 直接做索引
  -> slot 0 永远空着 (浪费一页)
  -> hart 4 会用到 slot 4, 即数组的第 5 个元素 -> 越界一页
```

本仓库用 `HartRange::contains()` / `to_cpu_id()` 集中处理, 并在
`platform/visionfive2.rs` 里写了编译期断言
`assert!(!VISIONFIVE2.harts.contains(0))` —— 把"顺手把 min 改成 0
试试"这个很自然但会导致真机随机卡死的动作挡在编译期。

## 中断控制器 (SiFive PLIC)

| 项目 | 值 | 出处 / 说明 |
|---|---|---|
| PLIC base | `0xc000000` | JH7110 内存映射 (**与 QEMU 的 0x0c000000 不同**) |
| PLIC size | `0x04000000` | 4 MiB 窗口 |

**关键教学点**: `drivers/src/irqchip/plic.rs` 的代码**一行都不
用改** —— 它只依赖 platform 提供的基地址, 不认识任何具体数字。
这就是"驱动描述设备协议, 平台描述设备位置"带来的复用。

## 定时器

| 项目 | 值 | 出处 / 说明 |
|---|---|---|
| timebase | `4 MHz` | (**QEMU 是 10 MHz**) |
| timer interval | `400000` tick | 4 MHz 下 = 0.1 秒, 与 QEMU 的时钟语义对齐 |
| timer kind | `Sbi` | **不使用 CLINT** |
| CLINT base | `0x02000000` | 只作为事实记录, 不访问 |

**为什么不用 CLINT**: 在真机上 U-Boot/OpenSBI 对 CLINT 的暴露方式
与 QEMU 不完全一致, 而直接访问的收益为零 (反正**设置**下一次中断
必须走 SBI, 因为 `mtimecmp` 是 M-mode 寄存器)。风险实实在在,
收益为零 —— 所以不用。

**如果 `timer_interval` 抄成了 QEMU 的 `1000000`**: 在 4 MHz 下
就是 0.25 秒, 表现为"VF2 上的进程切换明显更慢", 但**不会崩溃** ——
属于那种不查手册就永远发现不了的移植 bug。

## 串口 (16550 兼容)

| 项目 | 值 | 出处 / 说明 |
|---|---|---|
| UART0 base | `0x10000000` | 与 QEMU **恰好相同** (这是巧合!) |
| UART0 irq | `32` | PLIC 中断号 (**QEMU 是 10**) |
| UART0 clock | `24000000` Hz | 输入时钟 (**QEMU 是 3686400**) |
| 波特率 | `115200` 8N1 | 与 U-Boot 默认一致 |

### 这是移植时最常见的第一个 bug

```text
  抄成 3686400 (QEMU 的值)
  -> divisor = 3686400 / (16 * 115200) = 2
  -> 但真实时钟是 24 MHz, 应该 divisor = 13
  -> 实际波特率 = 24000000 / (16 * 2) = 750000, 是目标的 6.5 倍
  -> 症状: 串口输出**乱码**
```

而因为内核确实在运行 (它只是在用错误的时序发送字节), 这个现象
极容易被误判成代码逻辑问题。

**校验方式**: 启动横幅会打印
`uart16550 ready @ 0x10000000 divisor=13 irq=32`。

* `divisor = 24000000 / (16 * 115200) = 13.02` -> 13 ✓
* 如果打印出 2, 说明 `uart0_clock` 用了 QEMU 的值。

**注意 UART 地址与 QEMU 相同是个巧合** —— 不要因此以为"地址可以
不放在 platform 层"。中断号和时钟就不同, 而它们在同一个结构体里。

## 块设备 (Synopsys DesignWare MSHC / SDHCI 兼容)

| 项目 | 值 | 出处 / 说明 |
|---|---|---|
| SDIO0 base | `0x16000000` | JH7110 SD 控制器 |
| SDIO0 irq | `0` | 本课程用**轮询**, 不注册 SD 中断 |
| 设备型号 | `DesignWareMshc` | 见 `platform::BlockKind` |
| 初始化时钟 | `400 kHz` | SD 规范规定初始化阶段的上限 |
| 基准时钟 | `50 MHz` | 用于计算分频 |

**为什么不用 SD 中断**: 真机上 SD 中断的初始化流程 (卡检测、
稳压器、时钟门控) 通常需要设备树描述, 而那正是本课程刻意不引入
的东西。轮询在两个平台上行为一致。

**初始化时钟必须是 400 kHz**: SD 规范要求卡在上电后以不超过
400 kHz 的时钟完成识别。一上来就用 25 MHz, 大部分卡会**完全
不应答** (连 CMD0 都没有响应), 表现为"初始化超时"。而在 QEMU 上
测不到这一点 —— 那里没有真实的 SD 卡。这是"模拟器上通过、真机上
失败"的典型案例。

## 交付格式 (U-Boot FIT)

| 项目 | 值 |
|---|---|
| 格式 | FIT (Flattened Image Tree), `.itb` |
| load addr | `0x40200000` |
| entry addr | `0x40200000` |
| U-Boot 命令 | `bootm ${kernel_addr_r}` |

FIT 的属性会被 `cargo xtask image` 自动校验 (自校验 + `fdtget`
交叉验证)。见 `docs/board-deploy.md`。

## 已知的差异陷阱

| 陷阱 | 现象 |
|---|---|
| hart 区间写成 `0..3` | 只起来 3 个核, 无报错 |
| hart 区间写成 `0..4` | 试图启动 S7 监控核, 可能让 U-Boot 崩掉 |
| UART 时钟用了 3686400 | 输出乱码 |
| timer interval 用了 1000000 | 调度慢 2.5 倍, 无报错 |
| 内核加载地址用了 0x80200000 | 完全无输出 (那不在 JH7110 的 DRAM 里) |
| 直接用 CLINT 读时间 | 在真机上可能触发异常 |
| SD 初始化时钟用了 25 MHz | 卡不应答, 初始化超时 |
