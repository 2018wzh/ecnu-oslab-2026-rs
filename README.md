## 2. 从"面向字节"到"面向块"

磁盘有两个不能回避的事实:

1. **读写的最小单位是块(512字节)**

2. **每次读写都很慢**(毫秒级)

第1条决定接口形状, 第2条决定必须有缓存

### 2.1 缓冲区缓存

同一个块会被反复读取. 缓存把最近用过的块留在内存里:

```
   bread(blockno):
       命中    -> 直接返回, 引用计数 +1
       未命中  -> 找一个引用计数为 0 的块, 读磁盘, 放进去, 返回
```

**引用计数是这里最容易出错的地方**:

- `bread` 返回时 +1, 表示"有人正在用"

- 用完必须 `release`, -1

- 只有计数为0的块才能被回收

忘记 `release` 的症状: **跑到第30次读磁盘时卡死**(`NBUF = 30`, 缓存全被占满, 再也找不到可用块). 这是本阶段最典型的bug

### 2.2 LRU: 回收哪一块

把刚用过的块移到链表头部, 回收时从**尾部**取——尾部的就是最久没被用过的

`bwrite` 与 `release` 是两件事: **改过 ≠ 写完**

### 2.3 `bread` 里为什么不能在持锁时读磁盘

读磁盘很慢. 如果在持有缓存锁的时候读, 整个系统会在I/O期间完全停下来. 正确做法是:

```
   加锁 -> 找到位置 -> 标记"使用中" -> 【解锁】-> 读磁盘 -> 加锁 -> 放进链表
```

## 3. 位图: 哪些块是空闲的

磁盘第一个块是**超级块**, 记录全局信息(魔数、总块数、inode数、inode区起始块). 紧接着是位图: 每一位表示一个数据块是否已用

`find_free` 找第一个0——三个要点:

1. **返回的块号是"第几位"**, 不是字节下标. 算错会返回一个完全不相干的块

2. **位序**: 同一位图在不同实现里可能从低位或高位开始, 两端必须一致(mkfs与本函数)

3. **`i % 8` / `i / 8`**: 字节与位的关系别写反

**一个真实的坑**: 如果改成按32位字扫描, `1u32 << 32` 在RISC-V上会按位宽取模变成 `1 << 0`——于是你操作的是完全不相干的那一位, 而且没有任何报错

### 5.1 `bread` 的签名值得注意

```rust
pub unsafe fn bread(&mut self, dev: &mut dyn BlockDevice, blockno: usize) -> usize
```

- `&mut self`: 借用检查器保证"同一时刻只有一个地方在操作缓存"——这正是缓存需要的互斥, **不需要额外的锁**

- 返回 `usize`: 缓存块的下标, 调用者用它取数据

- `unsafe`: 里面要做原始指针访问

### 5.2 `submit`: 驱动里最容易写错的一步

```rust
unsafe fn submit(&mut self, mem: *mut VirtqueueMem,
                 sector: u64, buf: &mut [u8], is_write: bool)
                 -> Result<(), BlockError>
```

一次块请求要按VirtIO的协议走完五步:

```
   1. 填描述符链     请求头 (16B) -> 数据缓冲区 -> 状态字节 (1B)
   2. 发布到 avail 环  ring[avail_idx % N] = 链头;  avail.idx += 1
   3. 通知设备        QUEUE_NOTIFY
   4. 等设备完成      used.idx 前进；带超时
   5. 检查状态字节    0 = 成功；非 0 要报错，不能把坏数据当好数据用
```

四件必须想清楚的事:

1. **描述符的 `WRITE` 标志方向容易记反**: 它是**从设备的角度**看的——读操作时设备要往这块内存写, 所以带 `WRITE`; 写操作时不带

2. **`avail.idx` 必须在屏障之后才更新**, 否则设备可能读到一个"指向还没写好的描述符"的环项. 缺屏障的现象是**时好时坏**(经典症状: 加一句打印就能过, 去掉就超时)

3. **`used.idx` 必须用 `read_volatile` 读**: 普通读会被编译器提到循环外, 于是"设备明明完成了, 驱动却永远看不到"

4. **等的是"第N个完成", 不是"used.idx != avail_idx"**: 要在发布之前记下期望值, 否则会有隐蔽的竞态

另外两个已经给你写好的部分(`handshake` / `setup_queue`)里有两个坑, 值得对照着读: **队列长度要协商**(把 `QUEUE_NUM` 设成实际用的值, 且≤设备支持的最大值), 以及**读 `QUEUE_NUM` 之前要重新选队列**(读操作会改内部游标)

### 6.1 QEMU

```bash
cargo xtask run --config riscv64-qemu-virt
```

实现正确时应当看到:

```
[oslab-rs] 块设备自检: 按平台描述初始化
[oslab-rs]   设备: virtio-blk  容量: 2000 扇区
[oslab-rs]   开始读块 0 ...
[oslab-rs]   读块 0 成功, 超级块魔数 = 0x10203040  <- 与 mkfs 写入的一致, 块设备通路正常
```

**本阶段的验收标准**: 最后一行

`0x10203040` 是mkfs写进块0的魔数. 这个数字不对, 说明**读回来的内容和磁盘上的不是一回事**(常见原因: 队列协商错了、块号偏移算错了)

三个细节值得注意:

* **`设备:` 那一行打印的是驱动的名字**(`virtio-blk`), 而kernel里一行virtio代码都没有——设备探测与驱动选择都在 `drivers/` 层, kernel只拿到一个trait对象. VisionFive2上这里会打印SD驱动的名字

* **`容量: 2000 扇区`** 可以人工核对: `xtask disk` 生成的镜像就是2000个512字节的块

* **`开始读块 0 ...` 这一行是刻意加的**: 读操作可能卡在等待设备完成的循环里, 没有这行输出时"读失败了"与"读卡住了"在串口上看起来一模一样

### 7.1 缓存策略与统计

**为什么值得做**：这一章的核心就是缓冲区缓存，但"哪种淘汰策略更好"只有数据能回答。
本阶段要你实现的 `crates/kernel/src/fs/bio.rs` 的 `bread`，最朴素也最自然的写法就是"从 `hand` 指针开始扫第一个 `refcnt == 0` 的槽"——它只近似"最近没用过的优先"，槽位里没有任何年龄信息。
把策略做成可切换、把命中率打出来，你会第一次用**数字**评价一个内核设计选择，
也能亲眼看到"引用计数大于 0 的块不能被复用"这条不变式为什么必须存在。

**思路**：
- 先加统计：命中/未命中/淘汰次数/遇到"所有缓冲区都被引用"的次数，字段放在 `BufCache` 里最自然（缓存会成为全系统唯一的一份），再用一个 shell 命令打印。
- 再做可切换策略：把"找一个可复用的槽"抽成一个独立的策略函数，插入与淘汰的位置决定近似 LRU / FIFO / 随机替换；
  注意 `BufCache` 内部自带一把 `SleepLock`：换策略时只能改"挑哪个槽"，不能改变"取锁—扫描—替换—放锁"的临界区语义。
- 加法：**预读**——命中第 N 块时顺手把第 N+1 块读进来（顺序读的场景立刻见效）。
- 注意两个坑：被引用的块不能被淘汰（`Buf::refcnt`，`pinned()` 已经把它暴露出来）；
  预读会产生"还没人用"的块，要防止它们把缓存挤满导致"永远找不到可复用块"（本项目注释里正好记着这个坑）。
- 别把锁的粒度弄丢：`BufCache` 用的是 `crates/kernel/src/sync.rs` 的 `SleepLock`，
  而 README §2.3 问过"为什么不能在持锁时读磁盘"。顺手把它做掉——"加锁 → 找到槽 → 标记使用中 → 解锁 →
  读盘 → 加锁 → 放回"，统计与策略都不能改变"谁在什么时候持锁"。

**怎么算做到**：顺序遍历一个上百块的文件，两种策略的命中率差异可解释；
开预读后未命中次数下降；缓存接近满时系统仍能正常工作（不卡死）。

**涉及**：`crates/kernel/src/fs/bio.rs`、`crates/kernel/src/sync.rs`、`crates/kernel/src/console.rs`　**难度**：★★☆

### 7.2 MBR / GPT 分区表

**为什么值得做**：现在的磁盘镜像是"裸文件系统"——块 0 就是超级块
（`xtask/src/mkfs.rs` 写超级块、清位图，而内核侧现在是在 `crates/kernel/src/main.rs` 里直接读块 0 校验魔数 0x10203040）。
真实磁盘上有分区表。这条改的是**磁盘格式契约**：镜像生成工具与内核必须同时改，
正好把"磁盘格式是跨程序契约"这件事变成一次真实体验（也解释了为什么格式要写死字节序与对齐）。

**思路**：
- 镜像侧：在 `xtask/src/mkfs.rs` 的 `build_image` 里先在镜像头部写分区表，再把文件系统放进第一个分区；
  产物由 `xtask/src/main.rs` 的 `disk` 子命令生成，所以调试时从那里看入口。
- 内核侧：在"块设备 → 文件系统"之间加一层很小的分区解析，落点是 `crates/kernel/src/fs/adapter.rs` 的 `BlockAdapter`——
  它本来就是"把驱动的块接口变成文件系统的块接口"的那一层，加一个起始块偏移是对它语义最小的改动；之后所有块号都加这个偏移。
- 两种格式的差异要讲清：MBR 简单（一个扇区、4 个表项、小端）；
  GPT 复杂但更真实（主表 + 备份表、128 个表项、CRC32 校验、保护性 MBR）。
- **不要动默认镜像布局**：用新的配置或新的镜像文件（给 `xtask` 加一个选项即可），否则本分支的期望输出会失效。
- 签名与边界都要校验：分区表损坏时要明确报错（在"读超级块"那条路径上返回错误或停车打印原因），而不是被当成裸盘继续读。

**怎么算做到**：能挂载"带分区的镜像"并列出同一批文件（可读性对照实验）；
故意破坏签名 → 明确报错；分区越界（起始+长度超过设备）被拒绝。

**涉及**：`xtask/src/mkfs.rs`、`xtask/src/main.rs`、`crates/kernel/src/fs/adapter.rs`、`crates/kernel/src/main.rs`　**难度**：★★★

### 7.3 异步 IO：写回与请求队列

**为什么值得做**：本章实现的 `submit` 就是"发出去 → 在原地轮询等完成"：
它需要在自旋里用 `read_volatile` 等 used ring 前进，
一次只等一块，等待期间 CPU 什么也做不了。真实内核把请求排进队列、由中断驱动完成，
发起者可以继续跑或睡下去——这是"阻塞式驱动"到"中断驱动"的关键一步，也是本章的睡眠/唤醒在设备侧的第一个真实用途。

**思路**（两级，建议先做 L1）：
- **L1 延迟写（write-back）**：写操作只把块标成脏（`crates/kernel/src/fs/bio.rs` 的 `Buf` 已经有引用计数，加一个脏位），
  真正落盘交给一个后台时机（空闲时、定时器里、或缓存不够时批量刷）；读时若碰到脏块直接用内存里的内容。
- **L2 请求队列 + 中断驱动**：把"等待完成"从 `crates/drivers/src/block/virtio_blk.rs` 的 `submit` 里拆出来（拆成提交 + 中断处理两半），
  发起者睡在"请求完成"事件上；`crates/kernel/src/trap.rs` 的 `handle_external` 现在只是认领中断并打印，
  要按 `Claim::irq()` 分发到真正的设备处理函数，并用 `Plic::init_hart` 把 `PLATFORM.virtio0_irq` 使能。
- 两个必须处理的竞态：**提交与完成之间**（先检查再睡，或用锁串起来——本项目在等待子进程那处就真实踩过"丢唤醒"）；
  **设备报错**要能唤醒等待者并带回错误码（`BlockError` 已经是返回值，别丢掉它）。
- 别忘了多核：队列本身的互斥、以及"谁来发起下一次传输"；顺序读还要考虑"请求能不能合并"。
- SD 卡那条路径（`crates/drivers/src/block/sdhci.rs`）现在也是轮询，同样的改造在真机上更有意义。

**怎么算做到**：L1 连续写多个块只触发一次批量刷盘（打印批大小）；
L2 请求期间进程处于睡眠（用 shell 看进程状态），中断到来后被唤醒且数据正确；设备报错（模拟）时不卡死。

**涉及**：`crates/kernel/src/fs/bio.rs`、`crates/drivers/src/block/virtio_blk.rs`、`crates/kernel/src/trap.rs`、`crates/kernel/src/proc/proc.rs`　**难度**：★★★
